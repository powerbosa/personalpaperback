# personalpaperback

A personal **Paperback 0.8** extension repository, built with the pinned 0.8 toolchain
and deployed as a static site to GitHub Pages.

**Repository URL for Paperback 0.8:** `https://powerbosa.github.io/personalpaperback/`

For day-to-day use, see [HOW_TO_USE.md](./HOW_TO_USE.md). This file covers how it works.

---

## Why this exists

Paperback 0.8's Swift client decodes a repository manifest at
`<baseURL>/versioning.json`. Its decoder is strict: a missing key raises
`DecodingError.keyNotFound` and a wrong type raises `DecodingError.typeMismatch`, and
either one makes the app reject the **entire** repository rather than one extension.

The most common way to hit this is pointing Paperback 0.8 at a **Paperback 0.9**
repository. The 0.9 manifest format dropped the top-level `buildTime` key, so the 0.9
JSON parses fine and then fails to decode with exactly:

```
DecodingError.keyNotFound: Key 'buildTime' not found
```

`@paperback/toolchain@0.8.7` emits `buildTime` correctly — it is not a toolchain bug.
This repository is set up so that a manifest which could produce that error, or any
related decoding error, cannot be deployed in the first place.

## The 0.8 manifest schema

Generated by the toolchain into `bundles/versioning.json`:

```json
{
  "buildTime": "2026-08-17T21:59:54.080Z",
  "sources": [
    {
      "id": "Example",
      "name": "Example",
      "author": "powerbosa",
      "desc": "...",
      "website": "https://github.com/powerbosa",
      "contentRating": "EVERYONE",
      "version": "1.0.0",
      "icon": "icon.png",
      "tags": [{ "text": "Demo", "type": "info" }],
      "websiteBaseURL": "https://example.com",
      "intents": 5
    }
  ],
  "builtWith": { "toolchain": "0.8.7", "types": "0.8.7" }
}
```

`sources: []` is valid — an empty repository decodes fine and simply contains nothing.

Field definitions come from `@paperback/types@0.8.7` (`lib/base/SourceInfo.d.ts`) and
the toolchain's own `generateSourceInfo`. `contentRating` is one of `EVERYONE`,
`MATURE`, `ADULT`; badge `type` is one of `default`, `success`, `info`, `warning`,
`danger`; `intents` is a bitfield from the `SourceIntents` enum.

## Layout

```
src/                    production sources — what actually gets deployed
demo/Example/           pipeline self-test source; never deployed
scripts/
  lib/schema.mjs        the 0.8 schema as data; shared by both validators
  lib/inspect-source.mjs static inspection of a candidate source folder
  validate-manifest.mjs local pre-deploy gate
  validate-public.mjs   post-deploy gate, runs against the live HTTPS URLs
  add-source.mjs        safe install
  remove-source.mjs     safe removal
  list-sources.mjs      status of everything in src/
  bundle-demo.mjs       stages demo/ into src/, builds, then always unstages
  gen-health.mjs        writes the public health.json
bundles/                build output (gitignored); deployed to Pages
```

## Commands

| Command | Purpose |
| --- | --- |
| `npm run bundle` | Production build + local validation |
| `npm run bundle:demo` | Full pipeline self-test using `demo/Example` |
| `npm run validate` | Validate `bundles/versioning.json` |
| `npm run validate:public` | Validate the **live** deployment over HTTPS |
| `npm run list-sources` | List `src/` and flag broken sources |
| `npm run add-source -- <path>` | Install a source after inspection |
| `npm run remove-source -- <id>` | Remove a source |

## What the validators check

`validate-manifest.mjs` runs before deploy and fails the build on any of:

- `buildTime` missing, non-string, or not a parseable timestamp
- `builtWith` / `builtWith.toolchain` / `builtWith.types` missing or wrong type
- a toolchain or types version other than `0.8.7` (drift onto the 0.9 line)
- `sources` missing or not an array
- **any `null` or `undefined` entry in `sources`** — see below
- any source missing any decoder-required field, or with a wrong field type
- `contentRating` or badge `type` outside their permitted values
- a referenced `source.js` or `includes/<icon>` that doesn't exist on disk
- any `localhost`, loopback, RFC1918, link-local, `.local`, `file://` or absolute
  build-path string anywhere in the manifest or generated homepage

`validate-public.mjs` runs after deploy and re-runs all of the schema checks against
the bytes the CDN actually served, then fetches every referenced asset and
`health.json`. It retries while Pages propagates rather than treating a transient
404 as fatal.

### The `null` source problem

`generateVersioningFile` in the 0.8 toolchain pushes the result of a failed `.catch()`
into `sources`:

```js
const sourceInfo = await this.generateSourceInfo(file, directoryPath).catch(error => {
    this.log(`- ${file} ${error}`);
});
jsonObject.sources.push(sourceInfo);   // undefined on failure
```

`JSON.stringify` renders that `undefined` as `null`, so **one broken source silently
produces a manifest that breaks decoding of the whole repository** in the client. The
validator treats any `null` entry as a hard build failure and says so explicitly, so a
broken source fails the build instead of shipping a repository that bricks the app.

## Deployment

`.github/workflows/deploy.yml` on every push to `main`:

```
checkout → npm ci → verify pins → pipeline self-test → build → validate
        → health.json → configure Pages → upload artifact → deploy
        → fetch and validate the PUBLIC URLs → tag a rollback point
```

The workflow does **not** pass merely because the bundle step succeeded; if public
verification fails, the run fails. `actions/configure-pages` runs with
`enablement: true`, so Pages configures itself on the first run and never needs
touching in the repository settings.

Hosting is static GitHub Pages: nothing runs on any personal machine, and the URL
keeps serving with every local machine powered off.

## Version pinning

`@paperback/toolchain` and `@paperback/types` are pinned to exactly `0.8.7` — no
caret, no tilde — with `package-lock.json` committed and installed via `npm ci`.
`.github/dependabot.yml` explicitly ignores both packages, and CI re-asserts the
versions at build time. Paperback 0.9 is a different extension API and a different
manifest format; an automated bump would produce a repository this client cannot read.
